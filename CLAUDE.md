# Trainer platform: project context

Self-built indoor cycling platform. Priority order: telemetry core first, renderer second, world content last.
Protocol notes started from memory; items still marked VERIFY have not been checked against the spec or the trainer. FE-C pages were verified on 2026-10-06 (see Protocol notes).

## Owner context

- Go developer, Linux-first (PC, Raspberry Pi), macOS second. No Windows builds for now (owner's decision 2026-10-07).
- Values data ownership and self-hosting: local-first recording, no mandatory cloud, open formats (FIT).
- Rides with real shifters and cassette on a direct-drive trainer, so no virtual shifting is needed.
- Use case: casual free rides, occasional ERG sessions, optional group rides later.

## Hardware under test

- Trainer: Tacx Flux 2 Smart (T2980), confirmed over FE-C on 2026-10-06: manufacturer 89 (Tacx), model 2980, HW rev 1, firmware 4.503 (SW main 45, supplemental 3), ANT device number 47508, trans type 5.
  - Observed: pages 0x10 and 0x19 alternate at ~4 Hz, 0x50/0x51 interleaved, plus Tacx-specific 0xF0. Decoding of 0x10, 0x19, 0x50, 0x51 checked against live values (state transitions, coast-down speed, power, cadence).
  - Reports "resistance calibration required" and "user config required" until spin-down and page 0x37 are done.
  - Control verified 2026-10-06: page 0x37 (user config) clears the "user config required" flag; 0x33 at 4% gave ~265 W at 19.6 km/h, consistent with physics for the rider's mass; 0x31 ERG at 150 W held 149-150 W across 76-84 rpm.
  - Page 0x46 requests for 0x50/0x51 are answered (~0.5 s later). Requests for 0x47 command status are ignored in broadcast, ack and until-acked modes, although the profile requires a reply. Confirm setpoints via EVENT_TRANSFER_TX_COMPLETED and observed behaviour instead.
  - Rx fail rate 7-15% on this box; try stick placement.
  - Per retail specs: ANT+ FE-C and Bluetooth Smart (FTMS to be confirmed), electromagnetic brake, 7.6 kg flywheel, max 2000 W, max simulated grade 16%.
  - No descent simulation: the trainer can't drive the flywheel. The sim computes speed from physics (real grade) regardless. Following Zwift, descents are sent as grade × 0.5 × difficulty (negative); the Flux's brake should then go lighter than flat. VERIFY on a ride that negative grades feel lighter, not identical to 0 %.
  - Spin-down calibration over FE-C works (verified 2026-10-06, including one completed spin-down): page 0x01 request is acknowledged within 0.6 s, then the trainer alternates 0x02 and 0x10 (no 0x19, so no power or cadence during calibration). Its 0x02 page is `02 80 40 FF B8 22 FF FF`: speed too low, target 8.888 m/s (32 km/h), no temperature or target spin-down time.
  - It ignores the FE-C cancel (acknowledges it, keeps calibrating) and gives up exactly 64 s after the request, sending a failure response `01 00 00 FF FD FF FD FF` (0xFFFD where the spec says 0xFFFF for invalid). The core reports this honestly: "ignored the cancel" while it runs, cancelled when it ends.
  - Completed spin-downs via the TUI on 2026-10-06 (C forces one when the trainer doesn't ask): speed condition goes too-low → ok (stop pedalling) → too-low while coasting → success response; the trainer then reports status ok. The Flux reports no spin-down time: the success response carries 0xFFFD in the time and zero-offset fields (also in its timeout response). `fec` treats ≥ 0xFFFD as not reported, so nothing bogus (65533 ms) is shown or logged. Nothing left to build here.
- Radio: Tacx ANT+ USB stick, verified as `0fcf:1008` "ANT USBStick2" (Dynastream ANTUSB2) on the dev box (Linux 7.0).
  - The kernel's `usb_serial_simple` driver binds it and creates `/dev/ttyUSB*`. The Linux transport uses that tty in raw mode (`ant.OpenSerial`): no cgo, no libusb, no kernel driver detach. `deploy/udev/99-ant-usb.rules` gives group `ant` access and a stable `/dev/ttyANT` symlink. Verified on the dev box: reset, network key and FE-C channel open/close all ACKed over the tty.
- Keep the stick on a USB extension cable, away from USB 3 ports and other 2.4 GHz radios.
- Heart rate: ANT+ HRM on channel 1 (device type 120, period 8070, RF 57). It searches in low priority forever (high-priority search disabled), which per the protocol doesn't interrupt the trainer channel. Verified 2026-10-06: the ANTUSB2 accepts message 0x63 and the trainer kept ~3.9 Hz with the HRM channel searching. Not yet tested with a strap actually paired.
- The Flux 2 also broadcasts as separate ANT+ power and speed/cadence sensors; we don't need those channels because FE-C already carries power, cadence and speed.

## Architecture

```text
Trainer, HRM <-> ANT+ stick <-> telemetry service <-> sim core -> renderer (swappable)
                                                     |
                                                  recorder (FIT) -> export (intervals.icu, Garmin)
```

- Core in Go: telemetry service, sim core, recorder, export. Runs headless on Linux, including a Raspberry Pi or a container host with the stick attached.
- Renderer is a separate process connected over a local or LAN socket. Engine plan (owner's direction 2026-10-07: the owner does no coding or modelling, so worlds are procedural from GPX + DEM + OSM): a Go world builder turns a course into an engine-neutral package (DEM terrain with the road corridor matched to the profile, road ribbon from the track and OSM road tags, OSM buildings, trees, water) written as glTF plus a manifest; the renderer only loads glTF and follows the state stream. glTF over OBJ for models (Blender exports it; PBR, hierarchy, instancing). First 3D renderer: Godot 4 with C# (stable API across 4.x, runtime glTF loading, native gRPC client, editor optional); Three.js in a browser is the fallback, Bevy is out (API churn, Rust). Rides happen on a PC screen or a TV driven by a PC.
- Trainer control (grade, ERG target) stays inside the core on the USB side. The network only carries state to the renderer and requests from it (route, start, stop).

### What exists (2026-10-07)

- `ant`: framing, node/channels (incl. low-priority search), Linux tty transport, raw `FrameLog`.
- `telemetry.Stick` (owner's direction 2026-10-07: the core is stable without the stick, polling for it, never restart-looping): wraps `Service`, opens the stick when it appears (every 2 s), reopens it after an unplug (node read error ends `Service.Run`; trainer/HRM marked lost, readings cleared), keeps the user config across openings and sums the transport counters (metrics never go back). Commands without a stick answer `ErrTrainerUnavailable`. `State.Radio` / proto `Radio` (present, error; absent with `-fake`); TUI footer "✕ ANT+ stick not found: plug it in". A missing stick is logged once per distinct error. Checked under real systemd: no stick → service active, 0 restarts, API up.
- `fec`, `hrm`: ANT+ page codecs, checked against the specs.
- `telemetry`: `Run` drives the stick (trainer ch 0, HRM ch 1) into a `Hub`; `RunFake` produces a synthetic ride. The hub conflates: readers get the newest state, never a backlog, and never block the producer. Sensors are disabled / searching / connected / lost; readings clear when a sensor is lost or stale (5 s).
- `proto/osscycler/v1/telemetry.proto` → `gen/` (committed). Regenerate with `go generate ./` (buf via `go run`, plugins via `go tool`).
- `api`: gRPC `TelemetryService.StreamState`, bearer token on every call (min 16 chars, constant-time compare), refuses non-loopback without TLS on both server and client, default `127.0.0.1:7420`, default 60 Hz cap per client.
- `course`: GPX (stdlib XML) → course resampled in equal steps of at most 10 m. Elevation is first despiked (repeated running median, 5 wide, Tukey end-point rule: recordings often start with an altimeter glitch, e.g. +5.6 m on the first point gave a -36 % start), then smoothed over 60 m (Garmin exports quantise to 0.2 m), grade, gain/loss, full profile for renderers. `LoadDir` reads `*.gpx`; the file name is the course ID. `Position(d)` gives lat/lon along the original GPX track (kept beside the resampled profile, so corners aren't cut); the ride publishes it in its state (`Ride.Lat/Lon`, proto `latitude_deg/longitude_deg`).
- `sim`: power → speed with gravity, rolling resistance and aero drag (defaults: CdA 0.32, Crr 0.004, ρ 1.225, drivetrain 97.6 %); `TrainerGrade` follows Zwift's trainer difficulty (climbs × difficulty, descents × 0.5 × difficulty, capped at the trainer maximum). Default difficulty 50 %, as in Zwift.
- `ride`: course-ride session. `Start` arms a ride (trainer gets the opening grade), the clock starts at the first power > 0 and stops at the interpolated moment the line is crossed. Ticks at 4 Hz; a separate sender pushes the grade 1 s ahead (at current speed) when it changes by ≥ 0.1 % or every 5 s, then sends 0 % after the ride and leaves the trainer alone. Verified on the Flux 2 (arm → 0x33 pages acknowledged → abort → flat).
- `workout`: structured workouts as authored blocks (Warmup, SteadyState, Ramp, Cooldown, IntervalsT, FreeRide, MaxEffort; power as a fraction of FTP) with a flattened timeline for ERG, `.zwo` read/write (round-trips; layout from memory, VERIFY against real Zwift exports), `Watts(fraction, ftp, intensity)`. Native text format (`ParseText`/`FormatText`, one line per block, errors by line number, lossless both ways with .zwo). `Library`: a directory of .zwo files rescanned on every call; IDs from the API never build paths directly (new IDs must match a safe pattern), atomic writes. Telemetry has `SetTargetPower` (FE 0x31) on the service and the fake (fake power follows the target).
- `erg`: ERG workout session. Armed on start (opening target sent), clock from the first pedal stroke; keeps running 15 s after pedalling stops, then pauses until power returns. Targets = FTP × fraction × intensity (ramps continuous); free/max segments switch the trainer to flat grade; skip to next segment; text events shown 10 s. Sender re-sends every 5 s, hands the trainer back flat afterwards. Course rides and workouts exclude each other. Verified on the Flux 2: ERG page 0x31 acknowledged (80 W at 40 % of 200 W), flat after abort.
- API: `ListWorkouts`, `SaveWorkout`, `StartWorkout`, `StopWorkout`, `SkipSegment`, `SetIntensity`, `SetFtp`; workout progress in the state stream.
- `fit`: minimal FIT encoder/decoder of our own (no dependency): numeric base types, normal headers, header + CRC-16, `DecodePartial` for unfinished files (decoding our own files; no compressed timestamps or floats). Verified 2026-10-07 with Garmin's FIT SDK decoder (`@garmin/fitsdk` 21.218, run from the scratchpad, not a repo dependency): integrity OK, no errors, fields decode as intended.
- `home`: osscycler's folder, `~/osscycler` (visible on purpose, owner's decision 2026-10-07: riders drop GPX and .zwo files in, and back it up in one go; `OSSCYCLER_HOME` moves it): `profile.json`, `api-token` (mode 600, made by the core on first start), `courses/`, `workouts/`, `rides/`. Every core default points into it, so a release runs with no flags: `osscycler-core`, then `osscycler-tui` (which reads the token from it). Token precedence: explicit `-token-file`, then `$OSSCYCLER_API_TOKEN`, then the folder's file. On first start in the default folder only, a profile and rides from 0.1.0's XDG locations are moved in; a folder chosen with `OSSCYCLER_HOME` never takes them (a test once moved the owner's real profile that way; restored, and the rule added).
- `record`: FIT recorder, on by default (owner's decision 2026-10-07, Zwift-like): `-record DIR` defaults to `~/osscycler/rides`, `-no-record` turns it off; Makefile `RIDES ?= _rides` (empty → `-no-record`), demo `_demo/rides`. Ending a ride is the rider's choice too: `EndActivity` RPC (TUI: e outside a course ride or workout → END RIDE? with enter save as the default, d d discard (deletes the file), esc keep riding); after an end, no new file opens until the rider has stopped once. Idle timeout and core shutdown always save. Samples the hub at 1 Hz; one activity per riding session, opened at the first movement (power, cadence, or > 0.3 m/s, which counts coasting on a course), auto-paused after 3 s still (timer events), saved after 5 min still or on core shutdown (the core waits for it). Laps at each course-ride and workout start/end; course laps are `virtual_activity` with altitude, grade and the GPX position (`position_lat/long`, `-record-gps=false` leaves positions out), the rest `indoor_cycling`. Speed and distance: simulated on a course, the trainer's own otherwise, integrated so distance never jumps. Session has NP, FTP (`zones_target` + threshold_power), work, kcal ≈ kJ; device_info for creator, trainer and HRM. Written as `name.fit.part` (flushed every second, fsync every 30 s) and sealed to `name.fit`; on start, `.part` files left by a crash are finished from their own messages (torn last message dropped, an interrupted finish redone). Files are mode 600 (heart rate is health data). Finished course rides append a line to `results.jsonl` (course, time, power, difficulty, file + lap index: enough for ghosts later). State stream carries `Recording` (TUI footer: ● rec / ⏸ rec / ✓ saved, errors as warnings).
- `metrics`: OpenTelemetry metrics, off unless `OTEL_EXPORTER_OTLP_ENDPOINT` (or `..._METRICS_ENDPOINT`) is set (personal setting: `export OTEL_...` in `local.mk`, which make passes on to the core); `OTEL_SDK_DISABLED` / `OTEL_METRICS_EXPORTER=none` respected. OTLP/HTTP push every 15 s (`OTEL_METRIC_EXPORT_INTERVAL` overrides), final flush on shutdown bounded to 3 s, export failures logged at most every 10 min. Resource: `service.name` osscycler-core (→ Prometheus `job`), `service.version` from build info, a fresh `service.instance.id` per run (→ `instance`), host, plus `OTEL_RESOURCE_ATTRIBUTES`. All instruments are observed at export time (nothing on the radio path): `osscycler.ant.messages{direction}`, `.dropped_bytes`, `.bad_checksums`, `.overflows`, `osscycler.ant.channel.messages` and `.rf_events{channel,sensor,event}` (from new per-channel counters in `ant.Node.Stats().Channels`; RX fail rate = rf_events{EVENT_RX_FAIL} / (that + messages)), `osscycler.sensor.connected` / `.message_age{sensor}`, `osscycler.state.updates`, `osscycler.recording.active` / `.failed`. Verified 2026-10-07 against Prometheus 3.15 in Docker with its OTLP receiver.
- `replay` + `ride.Replay` (development and validation; `osscycler-replay` isn't in release archives): re-ride recorded course rides through the same session and ticks as a live ride (power held between the 1 Hz records; a gap over 2 s counts as stopped, while the ride clock runs on). `replay.Load(dir)` reads `results.jsonl` and each ride's lap from its FIT file; results now carry the sim parameters (`sim`: mass, CdA, Crr, air density, drivetrain) so a replay uses what the ride used. `replay/testdata` is a ride recorded by the real core (fake rider, Demo Hills from 1.48 km): the replay matches the live clock to 0.1 s (2:33.6 vs 2:33.5). `cmd/osscycler-replay` / `make replay` (`REPLAY_FLAGS="-cda 0.25"`, `-mass-kg`, `-crr` for what-ifs) lists recorded vs replayed times. To refresh the fixture: run the fake core with `-record replay/testdata -courses demo/courses -ride-start-m 1480`, start demo-hills over the API, let it finish.
- `history`: finished course rides from the recording directory's `results.jsonl` (read on every call, via `record.ReadResults`, which skips a half-written line), newest first, with each stretch's PB marked: a stretch is a course from a start point (within 1 m) over the same distance (within 5 m, so an edited GPX starts afresh); ties go to the earlier ride. `ListResults` RPC; the core reads history from the recording directory even with `-no-record`. TUI: the picker has COURSES / WORKOUTS / HISTORY tabs (tab / shift+tab, ←/→ cycle); COURSES shows each course's full-course PB, HISTORY lists rides with ★ PB.
- Ghosts: every course ride races the PB on its stretch, Zwift-style. `history.Store.Ghost` replays the PB's recorded lap (`ride.Replay` returns a trace: course position over the ride clock), scaled to finish on exactly the recorded time; `ride.Config.Ghosts` (a `ride.GhostSource`) loads it when a ride is armed, outside the session lock. The ride state carries `Ghost{Label, DistanceM, Gap, Elapsed}`; the gap is taken at the rider's position (rider's clock minus the ghost's time there, like a race time check), so at the line it is the difference in times. TUI: TIME tile "vs PB 7 Oct" with the gap under it (green ahead, red behind), magenta ghost marker on the course profile, "◆PB" on the look-ahead ruler when the ghost is within 250 m ahead, result screen "★ NEW PB" / "x s off your PB" / "first ride on this stretch". End to end on the fake core, a repeat of the fixture ride stayed within 0.1 s of its ghost throughout.

## Decisions so far

- ANT+ FE-C first, BLE FTMS as a second transport behind the same interface.
- State stream at about 60 Hz over gRPC server streaming (chosen 2026-10-06); control via reliable unary requests. Timestamp samples in the core with a monotonic clock; the renderer interpolates.
- Schema-first: state messages are in protobuf (control messages still to come). `api` tests run a real gRPC server over bufconn as the fake renderer.
- LAN API needs authentication from day one: bearer token from `OSSCYCLER_API_TOKEN` or `-token-file`, TLS required beyond loopback. It will be able to change trainer resistance.
- Operational metrics with OpenTelemetry, pushed over OTLP/HTTP only when `OTEL_EXPORTER_OTLP_*` names an endpoint; no pull endpoint (owner's decision 2026-10-07: the core is often off, and scraping would turn that into `up=0` noise; with push, no data simply means it wasn't running). Prometheus 3 can be the receiver itself (`--web.enable-otlp-receiver`, endpoint `/api/v1/otlp/v1/metrics`). Rider data (power, HR, position) never goes into metrics. Traces only when multiplayer brings a second service (`otelgrpc` then); logs stay on slog.
- Recorder writes FIT at 1 Hz to local disk, independent of any renderer connection, so a viewer crash never loses a ride.
- Workouts: our own text format is the native way to write them; Zwift `.zwo` is supported for import and export so workouts move freely between osscycler and Zwift (the owner keeps using Zwift elsewhere, at least until Zwift has a Linux build). Keep `.zwo` round-trips lossless. Never bundle or redistribute Zwift's own workouts or plans (their content; users import their own files), and mention Zwift only descriptively ("reads Zwift .zwo files"), no logos or implied affiliation. File formats aren't protected by EU copyright (CJEU C-406/10); no Zwift patent on the format was found (web search 2026-10-06, not a formal search; get one before any commercial release).
- Course rides are labelled FIT sub_sport `virtual_activity`, so platforms treat them as indoor/virtual rides (owner's decision 2026-10-07). The owner doesn't use Strava; for other users, Strava should then show them as Virtual Rides, off outdoor segment leaderboards (unverified).
- Container USB: with the tty transport, `--device /dev/ttyANT` is enough (major 188, ttyUSB). The libusb route would need the `/dev/bus/usb` node or a cgroup rule for major 189. Avoid `--privileged`.

## Working conventions for Claude Code

- Prefer small, testable packages: `ant`, `fec`, `hrm`, `telemetry`, `course`, `sim`, `ride`, `record`, `api`, `tui`.
- Never hardcode the ANT+ network key or any API token.
- Log raw frames behind a debug flag; hardware debugging needs them.
- Ask before adding heavy dependencies. Approved so far: gRPC + protobuf (buf for codegen), Bubble Tea v2 + Lip Gloss v2, OpenTelemetry metrics (`otel`, `sdk/metric`, `exporters/otlp/otlpmetric/otlpmetrichttp`; 2026-10-07).
- Directories starting with `_` are local only and git-ignored (`_antdocs/`, `_bin/`, `_logs/`, `_secrets/`, `_gpx/`, `_scratch/` for throwaway programs).
- One feature per commit (owner's preference); docs-only changes get their own `docs:` commit.
- CLAUDE.md is tracked and will ship with the source (owner's decision 2026-10-07: the owner works on several machines; no shame in AI-assisted development, the README says so). Keep it free of personal details; before the repo goes public, check it for the owner's body weight and the names of the owner's own routes.
- `make check` must pass before a commit or push: judge it by its exit code, never by filtered output (on 2026-10-07 two commits were pushed with a data race failing, hidden by a `grep` in the same command chain).
- Tests and manual runs never touch the rider's real data: use `t.TempDir()`, and for a manual run of the core set both `HOME` and `OSSCYCLER_HOME` to a scratch folder (on 2026-10-07 a run with only `OSSCYCLER_HOME` set moved the owner's real profile; restored, and the migration rule fixed).
- Rules about riding (what a ride needs, onboarding, who drives the trainer) live in the core and are enforced by the API; renderers only show them.
- Linux first, macOS second, no Windows. Build tools run pinned through `go run` (staticcheck, actionlint, nfpm, lipo), so nothing needs installing.
- Hardware-free checks used so far: the `-fake` core end to end over the API (throwaway drivers in `_scratch/`), Garmin's FIT SDK (`@garmin/fitsdk` from npm, in the scratchpad) for FIT files, Docker for packages (Debian, Fedora; real systemd in a privileged Fedora container) and for Prometheus with its OTLP receiver.
