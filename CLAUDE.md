# Trainer platform: project context

Self-built indoor cycling platform. Priority order: telemetry core first, renderer second, world content last.
Protocol notes started from memory; items still marked VERIFY have not been checked against the spec or the trainer. FE-C pages were verified on 2026-10-06 (see Protocol notes).

## Owner context

- Go developer, Linux-first (PC, Raspberry Pi), macOS second. No Windows builds for now (owner's decision 2026-10-07).
- Values data ownership and self-hosting: local-first recording, no mandatory cloud, open formats (FIT).
- Rides with real shifters and cassette on a direct-drive trainer, so no virtual shifting is needed.
- Use case: casual free rides, occasional ERG sessions, optional group rides later.

## Hardware under test

- Trainer: Tacx Flux 2 Smart (T2980), confirmed over FE-C on 2026-10-06: manufacturer 89 (Tacx), model 2980, HW rev 1, firmware 4.503 (SW main 45, supplemental 3), ANT device number 47508, trans type 5.
  - Observed: pages 0x10 and 0x19 alternate at ~4 Hz, 0x50/0x51 interleaved, plus Tacx-specific 0xF0. Decoding of 0x10, 0x19, 0x50, 0x51 checked against live values (state transitions, coast-down speed, power, cadence).
  - Reports "resistance calibration required" and "user config required" until spin-down and page 0x37 are done. The core logs every change of these flags ("trainer status"); on 2026-10-07 every connection reported resistance-cal-required, with no spin-down done that day. Whether a spin-down survives a power cycle is still to check: spin down, unplug, reconnect, and see whether the flag returns. The TUI shows the request as a quiet key hint (`c calibrate`, "recommended" in the menu), not a warning.
  - Control verified 2026-10-06: page 0x37 (user config) clears the "user config required" flag; 0x33 at 4% gave ~265 W at 19.6 km/h, consistent with physics for the rider's mass; 0x31 ERG at 150 W held 149-150 W across 76-84 rpm.
  - Page 0x46 requests for 0x50/0x51 are answered (~0.5 s later). Requests for 0x47 command status are ignored in broadcast, ack and until-acked modes, although the profile requires a reply. Confirm setpoints via EVENT_TRANSFER_TX_COMPLETED and observed behaviour instead.
  - Rx fail rate 7-15% on this box; try stick placement.
  - Per retail specs: ANT+ FE-C and Bluetooth Smart (FTMS to be confirmed), electromagnetic brake, 7.6 kg flywheel, max 2000 W, max simulated grade 16%.
  - No descent simulation: the trainer can't drive the flywheel. The sim computes speed from physics (real grade) regardless. Following Zwift, descents are sent as grade × 0.5 × difficulty (negative). Checked 2026-10-10 (manual control, ~22 km/h at ~70 rpm): -5 % took the same watts per km/h as 0 % (3.8 against 3.7-3.9): at that speed the Flux is already at its lightest, so descents can't feel lighter than flat.
  - Spin-down calibration over FE-C works (verified 2026-10-06, including one completed spin-down): page 0x01 request is acknowledged within 0.6 s, then the trainer alternates 0x02 and 0x10 (no 0x19, so no power or cadence during calibration). Its 0x02 page is `02 80 40 FF B8 22 FF FF`: speed too low, target 8.888 m/s (32 km/h), no temperature or target spin-down time.
  - It ignores the FE-C cancel (acknowledges it, keeps calibrating) and gives up exactly 64 s after the request, sending a failure response `01 00 00 FF FD FF FD FF` (0xFFFD where the spec says 0xFFFF for invalid). The core reports this honestly: "ignored the cancel" while it runs, cancelled when it ends.
  - Completed spin-downs via the TUI on 2026-10-06 (C forces one when the trainer doesn't ask): speed condition goes too-low → ok (stop pedalling) → too-low while coasting → success response; the trainer then reports status ok. The Flux reports no spin-down time: the success response carries 0xFFFD in the time and zero-offset fields (also in its timeout response). `fec` treats ≥ 0xFFFD as not reported, so nothing bogus (65533 ms) is shown or logged. Nothing left to build here.
- Radio: Tacx ANT+ USB stick, verified as `0fcf:1008` "ANT USBStick2" (Dynastream ANTUSB2) on the dev box (Linux 7.0).
  - The kernel's `usb_serial_simple` driver binds it and creates `/dev/ttyUSB*`. The Linux transport uses that tty in raw mode (`ant.OpenSerial`): no cgo, no libusb, no kernel driver detach. `deploy/udev/99-ant-usb.rules` gives group `ant` access and a stable `/dev/ttyANT` symlink. Verified on the dev box: reset, network key and FE-C channel open/close all ACKed over the tty.
- Keep the stick on a USB extension cable, away from USB 3 ports and other 2.4 GHz radios.
- Heart rate: ANT+ HRM on channel 1 (device type 120, period 8070, RF 57). It searches in low priority forever (high-priority search disabled), which per the protocol doesn't interrupt the trainer channel. Verified 2026-10-06: the ANTUSB2 accepts message 0x63 and the trainer kept ~3.9 Hz with the HRM channel searching. A real strap paired on 2026-10-07 (device 21326, trans type 209) and its data shows in the TUI.
- The Flux 2 also broadcasts as separate ANT+ power and speed/cadence sensors; we don't need those channels because FE-C already carries power, cadence and speed.

## Architecture

```text
Trainer, HRM <-> ANT+ stick <-> telemetry service <-> sim core -> renderer (swappable)
                                                     |
                                                  recorder (FIT) -> export (intervals.icu, Garmin)
```

- Core in Go: telemetry service, sim core, recorder, export. Runs headless on Linux, including a Raspberry Pi or a container host with the stick attached.
- Renderer is a separate process connected over a local or LAN socket. Engine plan (owner's direction 2026-10-07: the owner does no coding or modelling, so worlds are procedural from GPX + DEM + OSM): a Go world builder turns a course into an engine-neutral package (DEM terrain with the road corridor matched to the profile, road ribbon from the track and OSM road tags, OSM buildings, trees, water) written as glTF plus a manifest; the renderer only loads glTF and follows the state stream. glTF over OBJ for models (Blender exports it; PBR, hierarchy, instancing). First 3D renderer: Godot 4 with C# (stable API across 4.x, runtime glTF loading, native gRPC client, editor optional); Three.js in a browser is the fallback, Bevy is out (API churn, Rust). Rides happen on a PC screen or a TV driven by a PC.
- Trainer control (grade, ERG target) stays inside the core on the USB side. The network only carries state to the renderer and requests from it (route, start, stop).

### What exists (2026-10-07)

- `ant`: framing, node/channels (incl. low-priority search), Linux tty transport, raw `FrameLog`.
- `telemetry.Stick` (owner's direction 2026-10-07: the core is stable without the stick, polling for it, never restart-looping): wraps `Service`, opens the stick when it appears (every 2 s), reopens it after an unplug (node read error ends `Service.Run`; trainer/HRM marked lost, readings cleared), keeps the user config across openings and sums the transport counters (metrics never go back). Commands without a stick answer `ErrTrainerUnavailable`. `State.Radio` / proto `Radio` (present, error; absent with `-fake`); TUI footer "✕ ANT+ stick not found: plug it in". A missing stick is logged once per distinct error. Checked under real systemd: no stick → service active, 0 restarts, API up.
- `fec`, `hrm`: ANT+ page codecs, checked against the specs.
- `telemetry`: `Run` drives the stick (trainer ch 0, HRM ch 1) into a `Hub`; `RunFake` produces a synthetic ride; the fake rider pushes 30 W more per percent of trainer grade (m·g·v for ~80 kg at 4 m/s), so the course's grade and the difficulty show in its power (difficulty never changes the simulated speed, as in Zwift: it only changes what the trainer is sent). The hub conflates: readers get the newest state, never a backlog, and never block the producer. Sensors are disabled / searching / connected / lost; readings clear when a sensor is lost or stale (5 s).
- `proto/osscycler/v1/telemetry.proto` → `gen/` (committed). Regenerate with `go generate ./` (buf via `go run`, plugins via `go tool`).
- `api`: gRPC `TelemetryService.StreamState`, bearer token on every call (min 16 chars, constant-time compare), refuses non-loopback without TLS on both server and client, default `127.0.0.1:7420`, default 60 Hz cap per client.
- `course`: GPX (stdlib XML) → course resampled in equal steps of at most 10 m. Elevation is first despiked (repeated running median, 5 wide, Tukey end-point rule: recordings often start with an altimeter glitch, e.g. +5.6 m on the first point gave a -36 % start), then smoothed over 60 m (Garmin exports quantise to 0.2 m), grade, gain/loss, full profile for renderers. `LoadDir` reads `*.gpx`; the file name is the course ID. `Position(d)` gives lat/lon along the original GPX track (kept beside the resampled profile, so corners aren't cut); the ride publishes it in its state (`Ride.Lat/Lon`, proto `latitude_deg/longitude_deg`).
- `sim`: power → speed with gravity, rolling resistance and aero drag (defaults: CdA 0.32, Crr 0.004, ρ 1.225, drivetrain 97.6 %); the drag area scales with the rider's size (owner's direction 2026-10-07, as Zwift): `CdAFor(height, weight)` = 0.32 × Bassett et al. 1999 frontal area relative to the reference rider 1.80 m, 75 kg (1.95 m 90 kg → 0.358). The profile's optional `height_cm` (120–220, `-rider-cm` forces it) and the weight set it for rides started afterwards (`rider.Service.applyDrag` → `ride.Session.SetCdA`); without a height the reference 0.32 applies; an explicit `-cda` wins (`FixCdA`, published as `cda_forced`). `RiderProfile.cda` shows the one in effect. Computed once per profile change, never per tick (measured: no change in core CPU); `TrainerGrade` follows Zwift's trainer difficulty (climbs × difficulty, descents × 0.5 × difficulty, capped at the trainer maximum). Default difficulty 50 %, as in Zwift.
- `ride`: course-ride session. `Start` arms a ride (trainer gets the opening grade), the clock starts at the first power > 0 and stops at the interpolated moment the line is crossed. Ticks at 4 Hz; a separate sender pushes the grade 2 s ahead (at current speed; 1 s until 2026-10-10, when the owner felt every resistance change on the Flux come 1-2 s late) when it changes by ≥ 0.1 % or every 5 s, then sends 0 % after the ride and leaves the trainer alone. Verified on the Flux 2 (arm → 0x33 pages acknowledged → abort → flat).
- `workout`: structured workouts as authored blocks (Warmup, SteadyState, Ramp, Cooldown, IntervalsT, FreeRide, MaxEffort; power as a fraction of FTP) with a flattened timeline for ERG, `.zwo` read/write (round-trips; layout from memory, VERIFY against real Zwift exports), `Watts(fraction, ftp, intensity)`. Native text format (`ParseText`/`FormatText`, one line per block, errors by line number, lossless both ways with .zwo). `Library`: a directory of .zwo files rescanned on every call; IDs from the API never build paths directly (new IDs must match a safe pattern), atomic writes. Telemetry has `SetTargetPower` (FE 0x31) on the service and the fake (fake power follows the target).
- `erg`: ERG workout session. Armed on start (opening target sent), clock from the first pedal stroke; keeps running 15 s after pedalling stops, then pauses until power returns. Targets = FTP × fraction × intensity (ramps continuous); free/max segments switch the trainer to flat grade; skip to next segment; text events shown 10 s. Sender re-sends every 5 s, hands the trainer back flat afterwards. Course rides and workouts exclude each other. Verified on the Flux 2: ERG page 0x31 acknowledged (80 W at 40 % of 200 W), flat after abort.
- API: `ListWorkouts`, `SaveWorkout`, `StartWorkout`, `StopWorkout`, `SkipSegment`, `SetIntensity`, `SetFtp`; workout progress in the state stream.
- `fit`: minimal FIT encoder/decoder of our own (no dependency): numeric base types, normal headers, header + CRC-16, `DecodePartial` for unfinished files (decoding our own files; no compressed timestamps or floats). Verified 2026-10-07 with Garmin's FIT SDK decoder (`@garmin/fitsdk` 21.218, run from the scratchpad, not a repo dependency): integrity OK, no errors, fields decode as intended.
- `home`: osscycler's folder, `~/osscycler` (visible on purpose, owner's decision 2026-10-07: riders drop GPX and .zwo files in, and back it up in one go; `OSSCYCLER_HOME` moves it): `profile.json`, `api-token` (mode 600, made by the core on first start), `courses/`, `workouts/`, `rides/`. Every core default points into it, so a release runs with no flags: `osscycler-core`, then `osscycler-tui` (which reads the token from it). Token precedence: explicit `-token-file`, then `$OSSCYCLER_API_TOKEN`, then the folder's file. On first start in the default folder only, a profile and rides from 0.1.0's XDG locations are moved in; a folder chosen with `OSSCYCLER_HOME` never takes them (a test once moved the owner's real profile that way; restored, and the rule added).
- `record`: FIT recorder, on by default (owner's decision 2026-10-07, Zwift-like): `-record DIR` defaults to `~/osscycler/rides`, `-no-record` turns it off; Makefile `RIDES ?= _rides` (empty → `-no-record`), demo `_demo/rides`. Ending a ride is the rider's choice too: `EndActivity` RPC (TUI: e outside a course ride or workout → END RIDE? with enter save as the default, d d discard (deletes the file), esc keep riding); after an end, no new file opens until the rider has stopped once. Idle timeout and core shutdown always save. Samples the hub at 1 Hz; one activity per riding session, opened at the first movement (power, cadence, or > 0.3 m/s, which counts coasting on a course), auto-paused after 3 s still (timer events), saved after 5 min still or on core shutdown (the core waits for it). Laps at each course-ride and workout start/end; course laps are `virtual_activity` with altitude, grade and the GPX position (`position_lat/long`, `-record-gps=false` leaves positions out), the rest `indoor_cycling`. Speed and distance: simulated on a course, the trainer's own otherwise, integrated so distance never jumps. Session has NP, FTP (`zones_target` + threshold_power), work, kcal ≈ kJ; device_info for creator, trainer and HRM. Written as `name.fit.part` (flushed every second, fsync every 30 s) and sealed to `name.fit`; on start, `.part` files left by a crash are finished from their own messages (torn last message dropped, an interrupted finish redone). Files are mode 600 (heart rate is health data). Finished course rides append a line to `results.jsonl` (course, time, power, difficulty, file + lap index: enough for ghosts later). State stream carries `Recording` (TUI footer: ● rec / ⏸ rec / ✓ saved, errors as warnings).
- `metrics`: OpenTelemetry metrics, off unless `OTEL_EXPORTER_OTLP_ENDPOINT` (or `..._METRICS_ENDPOINT`) is set (personal setting: `export OTEL_...` in `local.mk`, which make passes on to the core); `OTEL_SDK_DISABLED` / `OTEL_METRICS_EXPORTER=none` respected. OTLP/HTTP push every 15 s (`OTEL_METRIC_EXPORT_INTERVAL` overrides), final flush on shutdown bounded to 3 s, export failures logged at most every 10 min. Resource: `service.name` osscycler-core (→ Prometheus `job`), `service.version` from build info, a fresh `service.instance.id` per run (→ `instance`), host, plus `OTEL_RESOURCE_ATTRIBUTES`. All instruments are observed at export time (nothing on the radio path): `osscycler.ant.messages{direction}`, `.dropped_bytes`, `.bad_checksums`, `.overflows`, `osscycler.ant.channel.messages` and `.rf_events{channel,sensor,event}` (from new per-channel counters in `ant.Node.Stats().Channels`; RX fail rate = rf_events{EVENT_RX_FAIL} / (that + messages)), `osscycler.sensor.connected` / `.message_age{sensor}`, `osscycler.state.updates`, `osscycler.recording.active` / `.failed`. Verified 2026-10-07 against Prometheus 3.15 in Docker with its OTLP receiver.
- `replay` + `ride.Replay` (development and validation; `osscycler-replay` isn't in release archives): re-ride recorded course rides through the same session and ticks as a live ride (power held between the 1 Hz records; a gap over 2 s counts as stopped, while the ride clock runs on). `replay.Load(dir)` reads `results.jsonl` and each ride's lap from its FIT file; results now carry the sim parameters (`sim`: mass, CdA, Crr, air density, drivetrain) so a replay uses what the ride used. `internal/replay/testdata` is a ride recorded by the real core (fake rider, Demo Hills from 1.48 km): the replay matches the live clock to 0.1 s (2:33.6 vs 2:33.5). `cmd/osscycler-replay` / `make replay` (`REPLAY_FLAGS="-cda 0.25"`, `-mass-kg`, `-crr` for what-ifs) lists recorded vs replayed times. To refresh the fixture: run the fake core with `-record internal/replay/testdata -courses demo/courses -ride-start-m 1480`, start demo-hills over the API, let it finish.
- `history`: finished course rides from the recording directory's `results.jsonl` (read on every call, via `record.ReadResults`, which skips a half-written line), newest first, with each stretch's PB marked: a stretch is a course from a start point (within 1 m) over the same distance (within 5 m, so an edited GPX starts afresh); ties go to the earlier ride. `ListResults` RPC; the core reads history from the recording directory even with `-no-record`. TUI: the picker has COURSES / WORKOUTS / HISTORY tabs (tab / shift+tab, ←/→ cycle); COURSES shows each course's full-course PB, HISTORY lists rides with ★ PB.
- Ghosts: every course ride races the PB on its stretch, Zwift-style. `history.Store.Ghost` replays the PB's recorded lap (`ride.Replay` returns a trace: course position over the ride clock), scaled to finish on exactly the recorded time; `ride.Config.Ghosts` (a `ride.GhostSource`) loads it when a ride is armed, outside the session lock. The ride state carries `Ghost{Label, DistanceM, Gap, Elapsed}`; the gap is taken at the rider's position (rider's clock minus the ghost's time there, like a race time check), so at the line it is the difference in times. TUI: TIME tile "vs PB 7 Oct" with the gap under it (green ahead, red behind), magenta ghost marker on the course profile, "◆PB" on the look-ahead ruler when the ghost is within 250 m ahead, result screen "★ NEW PB" / "x s off your PB" / "first ride on this stretch". End to end on the fake core, a repeat of the fixture ride stayed within 0.1 s of its ghost throughout.
- Rider profile and onboarding (owner's direction 2026-10-07: settings live with the installed program; onboarding is the stack's, renderers only show it). `profile`: `~/osscycler/profile.json` (`-profile` to move it), JSON, written atomically, mode 600: weight, FTP, difficulty, bike weight, and the rider's view in a 3D renderer (`view`: "chase", the default, or "eyes"; owner, 2026-10-09: a preference in the profile, so it follows the rider to any screen). Flags given explicitly (`-rider-kg`, `-ftp`, `-difficulty`) force a value for that run and are never saved, also when changed live; `local.mk` `CORE_FLAGS` are for testing only. `rider.Service` owns it in the core: applies changes (weight → trainer user config page 0x37 now and at every pairing via `SetUser`, and the mass of rides started afterwards; FTP → ERG; difficulty → rides), saves them, publishes `RiderProfile` in the state (`missing`: `weight_kg` / `ftp_w`, `suggested_ftp_w` = 2.5 W/kg), and gates the API: `StartRide` needs the weight, `StartWorkout` the FTP, else `FAILED_PRECONDITION` (`profile.ErrIncomplete`). `SetProfile` RPC (optional weight / FTP / height / view, all checked before any applies; out of range → `INVALID_ARGUMENT`); `SetFtp` and `SetDifficulty` save too. A broken profile file stops the core rather than being overwritten. TUI: onboarding form when `missing` is non-empty (weight, saved at once; then FTP prefilled from the core's suggestion), esc puts it off for the session, the menu's Profile edits later (owner, 2026-10-10: p and P both pause; the profile is the menu's); footer hint `m add your weight`. The demo uses its own `_demo/profile.json` (75 kg, 200 W).
- FIT export (owner's decision 2026-10-07: files only for now; external integrations much later): the core may be a Pi, so export goes over the API. `record.Catalog` lists finished recordings (session summary per file, cached by size and mtime; `.part` files never listed) and opens only names in the recorder's pattern (`YYYY-MM-DD-hhmmss.fit`), so no paths or traversal. `ListActivities` RPC; `ExportActivity` streams the file (size first, 64 KiB chunks), `api.DownloadActivity` is the client side. TUI: ACTIVITIES tab (date, riding time, distance, power, virtual/indoor, laps); s (or enter) saves the FIT file to `-export-dir` (default ~/Downloads, else home), via a temp file renamed when complete; an existing file is never overwritten.
- `control`: manual trainer control outside course rides and workouts: ERG watts (FE 0x31, 25-1000 W), a fixed grade (0x33, -10 % to `-max-grade`) or a brake level (0x30 basic resistance, 0-100 % in 0.5 % steps; works on the Flux, checked 2026-10-10: 20 / 40 / 60 % took 5.3 / 7.7 / 11.6 W per km/h). One driver at a time: manual control is refused during a course ride or workout, and they are refused while it is on (`State.Control.Mode`). Sends on change, resends every 5 s, retries while the trainer is away, sends flat once on release and then leaves the trainer alone. `SetTrainerControl` (oneof power_w / grade_pct / level_pct; clamped, the response has the target in effect) and `ReleaseTrainerControl` RPCs. TUI: on the dashboard w / g / l prompt for watts / grade (minus and decimals allowed) / level; while on, +/- step 5 W / 0.5 % / 5 % and x (or 0) goes back to free riding; the footer shows ERG 200 W / GRADE 6.0 % / LEVEL 40 %. Handy for the VERIFY items: whether negative grades feel lighter than flat, and how 0x30 behaves.
- Pause (owner, 2026-10-10: park the core for a coffee): `SetPaused` RPC, `State.paused` / `paused_since_unix_ms` (`telemetry.Hub.SetPaused`). While paused a course ride holds still (rider stopped, clock and ghost standing, trainer flat; on resume its clocks move on by the pause, so its time is riding time), a workout holds in its paused phase with the trainer flat (it carries on when pedalling resumes), manual control sends flat once and its target again on resume, and the recorder stops the timer at once and never ends the activity for being still (the 5 min count starts after the pause). A ride or lap that was paused (`Ride.paused`, `lap_paused`, `RideLap.paused`, results `paused`) is never a PB, never a ghost, can't be raced (`ErrPausedRide` → FAILED_PRECONDITION) and doesn't stop another ride being the PB. Starting a ride, a workout or manual control carries on (a refused start leaves the pause). TUI: p, P or space pauses and carries on (while nothing that takes keys is open), esc during a ride, workout or manual control pauses into the menu and esc out of it carries on (another screen carrying on closes that menu), a blue ⏸ PAUSED banner with how long. Checked on a `-fake` core on the oval: distance and clock stood for 10 s, speed 0, the timer stopped at once, carried on from the same clock. No screen (owner, 2026-10-10: quitting a screen, or its crashing, must not leave a ride hanging): screens open their state stream as a head (`StreamStateRequest.head`; the TUI and the 3D view do, also in debug mode (owner, 2026-10-10: a ride in the debug view, the only screen, was paused as unwatched); scripted runs (`--shot`, `--keys`) and scripts don't), counted in `State.heads`; `internal/unattended` pauses what is under way (a course ride armed or riding, a workout, manual control) 30 s after the last head went, and 30 minutes after ends it (ride stopped, workout stopped, control released) and saves the activity, lifting the pause; a head coming back finds it paused (P carries on). Checked on a `-fake` core: paused 31 s after the head's stream closed. Quitting (owner, 2026-10-10: q during a ride must not exit, the menu is where to quit from): q off the menu opens the menu, pausing what is under way as esc does; the menu's Quit (or q there) closes the screen, and with something under way and no other head asks first: enter end it, save the ride and quit; l quit and leave it paused; esc back to the menu (a ride ended or watched elsewhere meanwhile closes the screen as asked). A read-only TUI quits on q as before.
- `scenery` (2026-10-07): OpenStreetMap land use and buildings along each course. One Overpass query per 5 km stretch of a course (2026-10-08), asking for tiles on a fixed grid of degrees (`scenery/tiles.go`: 1/400° × 1/250°, ≈ 278 m; split 2× or 4× for narrow layers) within each layer's reach of the route: land use 300 m (whole tiles), buildings 100 m (¼ tiles, ≈ 70 m), roads 30 m and signs 25 m (¼), car parks 80 m (½); places 2 km as one box per stretch (nodes only). A tile goes to the first stretch that reaches it, so what the route passes twice (a loop's start and finish, an out-and-back) is asked for once; neighbouring tiles merge into rectangles (about 190 statements, 20 KB per query). Queries declare `[timeout:90][maxsize:128 MiB]` (the server admits small requests more readily; the defaults are 180 s and 512 MiB). `out geom`. Fetched on demand: only for a course being ridden (`StartRide` → `Store.Want(id, from)`), the stretch the ride starts in first, then the rest ahead, then behind; one fetch at a time, the latest wanted course first; retried after 1, 5, 15 and 60 min, then not until the course is ridden again; answers with an Overpass `remark` (timeout, overload) are never cached. A 429 (all of this client's slots taken: overpass-api.de allows 2, and a finished query holds its slot for a while) waits for a slot as `/api/status` tells, up to 2 min, 4 tries. Cache: `<courses dir>/.osm/<id>-<stretch>-<query hash>.json` (git-ignored), so a stretch is fetched once and again only when the GPX changes; saving a stretch removes its older files, stretches the course no longer has and the whole-course file from before stretches; the scenery is rebuilt from all cached stretches (merged, a way or relation in several kept once) as each arrives. Posbank Loop: 6 stretches, 10.7 MB, the scenery identical to the one-query build (14.1 MB; fixed 1 km boxes per stretch were 17.0 MB, 2.4 MB of it twice, 1.6 MB at the start and finish); buildings are most of it (5,500 fetched within 100 m, 2,472 drawn within 80 m; ½-size tiles fetched 7,200); stretch 0 arrived 19 s into a ride (was 1½ min for everything). Overpass usage guidelines (checked 2026-10-08): about 10,000 queries and 1 GB a day for one-off use, divided by 100 for regular use (under 100 queries and 10 MB a day), counted per application over all its users; fine for one rider with a cache, not for many: see Open questions. caching is king (owner, 2026-10-07: the public server is often overloaded, 504s seen the same day). `-osm=false` uses the cache only, `-osm-url` picks the server. `Build` classifies left/right × near 15 m / far 60 m per profile sample (point in polygon, even-odd over all multipolygon edges, smallest bounding box wins so a park inside a residential area is a park) and turns buildings within 80 m into road-aligned boxes (height from `height`, `building:levels`, else by kind; kept 4 m off the road). Proto `Course.land_use` (4 bytes per sample), `buildings`, `attribution` (ODbL credit, shown by renderers). The TUI shows the credit in the start menu only (owner's direction 2026-10-08, to save space, and 2026-10-10: not on rides at all, where it had shown for a ride's first 20 s; the OSMF attribution guidelines allow a startup/menu screen for games and simulations, as long as nobody has to look for it). Big enclosing polygons with no nodes near the route are missed (falls back to grass). ## Decisions so far

- Public on GitHub under GPL-3.0 (owner's decision 2026-10-07). Security reports go through GitHub's private vulnerability reporting (SECURITY.md). The release workflow's actions are pinned to commits; update them by looking up the new tag's commit. Releases are immutable once published (owner's decision 2026-10-07), so the workflow only drafts them (every file attached, notes from notes/<tag>.md); the owner checks the draft and publishes it. A fix after publishing is a new version, never a moved tag. The `check` workflow runs `make check` and actionlint on every push and pull request with no secrets (read-only token, `pull_request`, never `pull_request_target`); the `main` ruleset blocks deletion and force pushes, and can require the `check` job.
- Releases so far: v0.1.0, v0.2.0, v0.2.1 (2026-10-07), v0.3.0 (published 2026-10-09: the included Posbank Loop, the road view's junctions, car parks and place-name signs, map data only for the course being ridden, the GPL in every download; notes in `notes/v0.3.0.md`; no full ride of the Posbank Loop on the Flux before it, by the owner's choice). 0.2.2 was never released: its notes went into 0.3.0's. v0.4.0 (published 2026-10-10: the 3D view and the world builder, `osscycler` as one command, ready-built worlds for the Posbank Loop and the test tracks; notes in `notes/v0.4.0.md`).
- ANT+ FE-C first, BLE FTMS as a second transport behind the same interface.
- State stream at about 60 Hz over gRPC server streaming (chosen 2026-10-06); control via reliable unary requests. Timestamp samples in the core with a monotonic clock; the renderer interpolates.
- Schema-first: state messages are in protobuf (control messages still to come). `api` tests run a real gRPC server over bufconn as the fake renderer.
- LAN API needs authentication from day one: bearer token from `OSSCYCLER_API_TOKEN` or `-token-file`, TLS required beyond loopback. It will be able to change trainer resistance.
- Operational metrics with OpenTelemetry, pushed over OTLP/HTTP only when `OTEL_EXPORTER_OTLP_*` names an endpoint; no pull endpoint (owner's decision 2026-10-07: the core is often off, and scraping would turn that into `up=0` noise; with push, no data simply means it wasn't running). Prometheus 3 can be the receiver itself (`--web.enable-otlp-receiver`, endpoint `/api/v1/otlp/v1/metrics`). Rider data (power, HR, position) never goes into metrics. Traces only when multiplayer brings a second service (`otelgrpc` then); logs stay on slog.
- Recorder writes FIT at 1 Hz to local disk, independent of any renderer connection, so a viewer crash never loses a ride.
- Workouts: our own text format is the native way to write them; Zwift `.zwo` is supported for import and export so workouts move freely between osscycler and Zwift (the owner keeps using Zwift elsewhere, at least until Zwift has a Linux build). Keep `.zwo` round-trips lossless. Never bundle or redistribute Zwift's own workouts or plans (their content; users import their own files), and mention Zwift only descriptively ("reads Zwift .zwo files"), no logos or implied affiliation. File formats aren't protected by EU copyright (CJEU C-406/10); no Zwift patent on the format was found (web search 2026-10-06, not a formal search; get one before any commercial release).
- Course rides are labelled FIT sub_sport `virtual_activity`, so platforms treat them as indoor/virtual rides (owner's decision 2026-10-07). The owner doesn't use Strava; for other users, Strava should then show them as Virtual Rides, off outdoor segment leaderboards (unverified).
- Container USB: with the tty transport, `--device /dev/ttyANT` is enough (major 188, ttyUSB). The libusb route would need the `/dev/bus/usb` node or a cgroup rule for major 189. Avoid `--privileged`.

## Working conventions for Claude Code

- Prefer small, testable packages: `ant`, `fec`, `hrm`, `telemetry`, `course`, `sim`, `ride`, `record`, `api`, `tui`. They all live under `internal/` (2026-10-08), so nothing is promised to outside importers and the repo root stays tidy; package names in these notes mean `internal/<name>`. The only importable Go package is `gen/` (the protobuf bindings, for Go clients of the API). Moving a package out of `internal/` later is non-breaking; moving one in is not.
- Never hardcode the ANT+ network key or any API token.
- Log raw frames behind a debug flag; hardware debugging needs them.
- Ask before adding heavy dependencies. Approved so far: gRPC + protobuf (buf for codegen), Bubble Tea v2 + Lip Gloss v2, OpenTelemetry metrics (`otel`, `sdk/metric`, `exporters/otlp/otlpmetric/otlpmetrichttp`; 2026-10-07). In the Godot renderer only (C#, 2026-10-08): `Grpc.Net.Client`, `Google.Protobuf`, `Grpc.Tools`.
- Directories starting with `_` are local only and git-ignored (`_antdocs/`, `_bin/`, `_logs/`, `_secrets/`, `_gpx/`, `_scratch/` for throwaway programs).
- One feature per commit (owner's preference); docs-only changes get their own `docs:` commit.
- Branches (owner's decision 2026-10-07; DEVELOPMENT.md has the steps): work on a branch from `develop` and open a pull request into `develop` (the default branch); never push to `main`. `main` holds releases only: a pull request from `release/X.Y` or `hotfix/X.Y.Z` of this repository (the `release-branch` check), merged with a merge commit, then tagged `vX.Y.Z` on that merge (the release workflow refuses tags not on `main`), and `develop` brought up to `main`. Rulesets enforce it: no deletion or force push on either branch, `check` required on both, pull requests and merge commits on `main`; `v*` tags can't move or be deleted.
- A fault in a built world (holes, roads missing or torn at junctions, land through the road, the rider off the road or hopping roads): load the `world-faults` skill (`.claude/skills/world-faults/`) and work in its order, ending with the fix in the builder, a test that fails without it and, where it can catch it, a guard in `World.Check`.
- Making anything the 3D world or renderer draws (plants, buildings, props, bridges, avatars, HUD graphics): load the `world-assets` skill (`.claude/skills/world-assets/`): where an asset belongs, how it is made in code, licences, checks, Godot pitfalls. This file keeps what exists and the owner's verdicts.
- The 3D work (world builder, renderers) was built on the long-lived private branch `world` (repository `digimago/osscycler-world`, 2026-10-08 to 2026-10-10) and came into develop as one squashed pull request for 0.4.0 (owner's choice 2026-10-10; its 270 commits stay in that private repository). From then on 3D work goes like any other: a branch from develop and a pull request. The `world` branch and the private repository are kept for their history only; don't build on them.
- CLAUDE.md is tracked and will ship with the source (owner's decision 2026-10-07: the owner works on several machines; no shame in AI-assisted development, the README says so). Keep it free of personal details: no body weight, no names of the owner's own routes, nothing that places the owner's home. The repo went public in October 2026; before that the history was rewritten (git fast-export, a local script, fast-import) to take those out, every branch but main was deleted, and v0.1.0 and v0.2.0 were re-tagged and rebuilt.
- `make check` must pass before a commit or push: judge it by its exit code, never by filtered output (on 2026-10-07 two commits were pushed with a data race failing, hidden by a `grep` in the same command chain).
